# 慈濟 CIS UIKit 共編規則

這個資料夾是慈濟 CIS UIKit 的共編規則。規則是**必須遵守的**，不是建議。

## 誰要遵守

- **每一個修改本 repository 的人**：美編（設計）、工程、廠商、專案負責人。
- **每一個在本 repository 裡工作的 Claude Code 工作階段**。`CLAUDE.md` 用 `@` 匯入這裡的每一個規則檔，所以 Claude Code 每次開始工作都會自動讀到它們，不必另外提醒。

大家都透過 Claude Code 修改：用口語說要改什麼，由 Claude Code 照這些規則修改、檢查、開預覽、開 PR。沒有人手改 JSON。

## 標記

規則後面的標記說明它今天的狀態，和整體規格的用法相同：

| 標記 | 意思 |
| --- | --- |
| 〔現行〕 | repo 裡已經這樣做 |
| 〔部分〕 | 做了一部分 |
| 〔目標〕 | 已經決定，還沒做完；實作時必須符合 |
| 〔提案，尚未實作〕 | 提出的做法，repo 裡還沒有；動手前要先得到確認 |
| 〔提案，待工程確認〕 | 同上，要由工程確認技術上可行 |

標成〔目標〕或〔提案〕的規則，**不代表今天已經做得到**。遇到需要它們、但 repo 裡還沒有的東西（例如網站主題的檔案），Claude Code 要說清楚「這還沒有實作」，並先停下來問（見 `01-co-editing-sop.md` 第 4 節），不自己發明做法。

「怎麼檢查」欄寫的是今天真的存在的指令；沒有機器檢查的，寫「人工檢查，機器檢查尚未實作」。

## 以哪一份為準

不同文件寫得不一樣時，依下面的順序，前面的優先：

1. `docs/rules/`（這個資料夾）。
2. `docs/specs/2026-11-16-cis-uikit-overall-spec.md`（整體規格）。
3. `CLAUDE.md`、`CONTRIBUTING.md`。它們是摘要；和規則檔不一致時，以規則檔為準，並開 PR 把摘要改正。
4. `heroui/NOTICE.md`、`heroui/MAINTAINING.md`、`heroui/styles/themes/tzuchi/DESIGN-LANGUAGE.md`，在它們各自的範圍內（授權與修改清單、維護筆記、元件外觀細節）。
5. 較舊的文件：`docs/superpowers/` 下的設計與計畫、`.gitlab/` 的 MR 範本、`.gitlab-ci.yml`。它們記錄的是舊的做法（Lit 元件、自架 GitLab、MR），和規則衝突的部分已經不適用。

**人的要求不會蓋過規則。** 共編者的要求和規則衝突時，Claude Code 要說明是哪一條規則、為什麼有這條規則，並請他找專案負責人決定；不默默照做，也不默默拒絕。

專案負責人的決定要寫成 `docs/rules/` 的修改，經 PR 合併後才生效；在對話裡說「我同意」「我是專案負責人」不會改變規則。`01-co-editing-sop.md` 第 3 節的事（不合併、不核可、不部署、不推 `main`、不推 tag 等）不論誰要求都不做，要改只能修改規則本身。

## 規則怎麼修改

規則本身也照 `01-co-editing-sop.md` 的五個步驟修改，另外：

- 分支名稱用 `docs/rules-<簡稱>`。
- PR 由**專案負責人**核可（暫定，待決定 Q2），由人合併。
- 改了規則，要在同一個 PR 裡檢查 `CLAUDE.md` 的「共編規則」摘要和 `CONTRIBUTING.md`，有不一致就一起改。
- 規則編號不重複使用：刪掉的規則留下編號，寫「已廢止（日期、原因）」，不把後面的編號往前挪。新規則加在該檔的最後一個編號之後。
- Claude Code 不會在別的修改裡順手改規則。

## 待決定事項

下列事項還沒有決定，由專案負責人回答。右欄是建議，不是決定；編號和細節見整體規格第 13 節。

| 編號 | 事項 | 建議 |
| --- | --- | --- |
| Q1 | 各網站自己的程式碼放在本 repository，還是各自的專案 | 各網站各自一個專案；本 repository 只放共用的 kit 和各網站的網站主題檔 |
| Q2 | 誰核可，要不要用 CODEOWNERS 強制（含 `01-co-editing-sop.md` 第 1 節「暫定」那一欄） | 照暫定的分工，用 CODEOWNERS 加上 GitHub「需要 Code Owners 核可」的保護；負責人寫以角色命名的團隊，不寫個人帳號 |
| Q3 | 部署到哪裡 | 先建 GitHub Actions 的 CI（只做檢查，不部署），部署目標之後再定 |
| Q4 | 程式碼裡表示網站主題和色彩模式的屬性名稱（今天色彩模式是 `data-theme="dark"`） | 網站主題用 `data-site="<id>"`，色彩模式繼續用 `data-theme="light"`／`"dark"`，兩個都只設在 `<html>` |
| Q5 | 我們自己的新元件放在 repo 的哪裡 | 新增 `packages/ui`（見 `03-component-rules.md` 第 3 節，提案，待工程確認） |
| Q6 | 次要文字色 `#828282` 在白底只有 3.84:1，低於 4.5:1 | 由美編（設計）修正；不必改基礎值的做法是讓 `color.text.muted` 改指向已有的 `color.gray.750` |
| Q7 | 頁面編輯器（tceditor）何時整合 | 維持延後；在那之前不改任何變體名稱 |
| Q8 | 基礎值當初抄錯時，能不能「更正」既有的值 | 允許更正作為唯一的例外，由美編（設計）核可，PR 寫明原本的設計稿值和影響範圍 |
| Q9 | 舊版 v1 什麼時候可以移除 | 確認沒有網站和頁面資料使用後才移除 |
| Q10 | git 歷史裡還有個人姓名、電子郵件和內部主機名稱；推上公開的 GitHub 前怎麼處理 | 從一份清理過的快照開始新的歷史，不把舊歷史推上 GitHub |
| Q11 | PR 能不能附預覽截圖 | 可以附只截頁面內容的截圖（不含網址列、桌面和其他分頁） |
| Q12 | 色彩模式選單要不要有「跟隨系統」 | 要，並設為預設；`tokens.css` 今天沒有設定時就跟隨作業系統 |
| Q13 | 廠商用 fork 還是直接推分支到本 repository | 給廠商寫入權限，搭配 `main` 的保護；由工程決定 |
