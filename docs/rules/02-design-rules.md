# 02 設計規則：tokens、網站主題、色彩模式、變體、版本、三級判斷

每一條規則有編號、一句規則、為什麼，以及「怎麼檢查」。「怎麼檢查」寫的是今天真的存在的指令；沒有機器檢查的，寫「人工檢查，機器檢查尚未實作」。依據：整體規格第 2、6、7、8.2 到 8.4 節。

規則編號 R-D-xx。

## 1. 用詞

| 編號 | 規則 | 為什麼 | 怎麼檢查 |
| --- | --- | --- | --- |
| R-D-01 | 「主題」這個詞只用來指**網站主題**，也就是「哪一個網站」的外觀（例如慈濟入口網、慈濟環保網、年報網）。 | 網站會有 10 到 20 個，同一個詞指兩件事，大家會講錯要改的東西。 | 人工檢查，機器檢查尚未實作 |
| R-D-02 | 淺色、深色叫**色彩模式**，不叫「主題」「深色主題」「暗色」。網站主題和色彩模式互相獨立，可以自由組合：每一個網站主題都有淺色和深色。 | 色彩模式是讀者的選擇，網站主題是網站的身分，兩者要能分開切換。 | 人工檢查，機器檢查尚未實作 |
| R-D-03 | 其他用詞固定：**基礎 Foundations**（所有網站共用的色階和刻度，程式裡叫 primitive）、**語意色**（說明用途的顏色，程式裡叫 semantic）、**元件 token**（某個元件專用的值）、**變體 variant**（同一個元件的幾種設計或選項）、**版本**（只用整數 v1、v2）。人員只寫職稱（唯一的例外見 R-D-34）。 | 文件、PR、手冊和 Claude 的回覆用同一套詞，才不會誤會。 | 人工檢查，機器檢查尚未實作 |
| R-D-34 | R-D-03「人員只寫職稱」的例外：**手冊**裡可以用廠商的公司名稱「致遠」稱呼廠商；每一頁第一次出現寫「致遠（廠商）」，之後寫「致遠」。這是專案負責人的決定。其他人員仍然只寫職稱，不寫姓名；手冊以外的檔案（規則、`CONTRIBUTING.md`、PR）照 R-D-03 寫「廠商」。 | 專案負責人決定讓手冊的讀者知道廠商是哪一家；這是公司名稱，不是個人姓名。 | 人工檢查，機器檢查尚未實作 |

## 2. tokens

tokens 分三層，都在 `packages/tokens/src/`：

| 層 | 放哪裡 | 例子 | 怎麼改 |
| --- | --- | --- | --- |
| 基礎 Foundations | `primitive/`（color、elevation、scale、typography） | `color.blue.900`、`space.16`、`radius.md` | 只新增，不修改既有的值 |
| 語意色（含語意字級） | `semantic/` | `color.brand.primary` → `{color.blue.900}` | 可以改成指向另一個基礎值 |
| 元件 token | `component/`（今天 33 個檔） | `button.radius` → `{radius.md}` | 可以改值；新增時每個只定義一次 |

| 編號 | 規則 | 為什麼 | 怎麼檢查 |
| --- | --- | --- | --- |
| R-D-04 | 顏色、字級、間距、圓角、陰影的值只寫在 `packages/tokens/src/**/*.tokens.json`（DTCG 格式）；網站主題的檔案（提案，R-D-17 的 `sites/<id>/theme.*.json`）實作後也是這個唯一來源的一部分。CSS 變數、HeroUI 的慈濟主題、手冊和 Storybook 都由程式從它產生，不在任何地方手抄色碼或數值。 | 只有一個來源，改一次就全部跟著變，不會有兩個地方的值不一樣。 | `pnpm --filter @tzuchi/tokens test` 檢查產物能建出來；手冊和 Storybook 有沒有手抄值：人工檢查，機器檢查尚未實作 |
| R-D-05 | `heroui/styles/themes/tzuchi/variables.css` 是產生的檔案，不手改。改完 tokens 要執行 `pnpm run heroui:theme` 重新產生。 | 手改的值會在下一次產生時被蓋掉，也會和 tokens 對不上。 | `git add` 之後跑 `pnpm run heroui:theme && git diff --exit-code -- heroui/styles/themes/tzuchi/variables.css`（SOP 步驟 4） |
| R-D-06 | 基礎 Foundations 只新增，不修改既有的值。要換顏色，就新增一個基礎色（需要的話，由美編（設計）核可），再讓語意色或元件 token 指向它。 | 基礎是所有網站共用的刻度；改一個既有的值，所有網站、所有用到它的地方會一起變。 | 人工檢查，機器檢查尚未實作 |
| R-D-07 | 語意色和元件 token 都用參照指向下一層（例如 `{color.blue.900}`），不寫死色碼。 | 寫死色碼，色彩模式和網站主題就換不掉它。 | 深色模式：`pnpm --filter @tzuchi/tokens test`（`check.mjs` 檢查深色的顏色都是參照）；淺色和元件層：人工檢查，機器檢查尚未實作 |
| R-D-08 | 每個元件 token 只在 `packages/tokens/src/component/` 定義一次。色彩模式和網站主題只覆寫既有的名稱，不另外定義。 | 同一個值定義兩次，就不知道哪一個才有效。 | 人工檢查，機器檢查尚未實作 |
| R-D-09 | 改名保護（先棄用、後移除，由機器檢查）完成之前，**沒有人**改 token 的名稱，也不刪除 token。 | 網站、HeroUI 的慈濟主題和頁面編輯器都用這些名稱；改掉一個，用到它的地方會悄悄失效。改名保護是提案，尚未實作。 | 人工檢查，機器檢查尚未實作 |
| R-D-10 | 新增 token 和修改值，照 SOP 做即可。新的 token 名稱要由美編（設計）確認。新的 token 不可以只是既有 token 的別名（值就是 `{另一個 token}`、用途也相同）：這種需求其實是改名，列入命名規範那一次的改名（R-D-11）。CSS 變數一律用 `--tc-` 前綴，層級用 `-` 連接（例如 `--tc-color-brand-primary`）；色階用 `color.<色名>.<階>`。 | 名稱一旦被用了就不能改（R-D-09），所以要在新增時就取對。 | 前綴由 `packages/tokens/style-dictionary.config.mjs` 的 `prefix: 'tc'` 產生；`check.mjs` 只檢查幾個必備變數存在；名稱好不好：人工檢查 |
| R-D-11 | 美編（設計）的命名規範，等改名保護完成後，以一次規劃好的改名套用，不零星改名。 | 零星改名會讓新舊名稱長期混在一起。 | 人工檢查，機器檢查尚未實作 |

## 3. 色彩模式

| 編號 | 規則 | 為什麼 | 怎麼檢查 |
| --- | --- | --- | --- |
| R-D-12 | 預設網站的深色模式只覆寫語意色和陰影（`packages/tokens/src/themes/dark/`），不重新定義基礎值；深色的顏色值必須是指向基礎色的參照，不寫死色碼。 | 深色模式是「換一組指向」，不是另一套顏色；這樣元件 token 會自動跟著換。 | `pnpm --filter @tzuchi/tokens test`（`check.mjs`） |

## 4. 網站主題

今天 repo 裡只有**預設網站主題（慈濟入口網）和它的深色模式**。其他網站的檔案是提案，尚未實作。

| 編號 | 規則 | 為什麼 | 怎麼檢查 |
| --- | --- | --- | --- |
| R-D-15 | 預設網站主題是慈濟入口網：今天 `packages/tokens/src/` 的值就是它。沒有指定網站時就用它。 | 每個網站都從同一個預設出發，只寫不同的地方。 | 人工檢查（Storybook 預設開在 `tzuchi`） |
| R-D-16 | 網站主題和色彩模式都只設在 `<html>` 上，不設在頁面裡的其他元素。一頁一次只套一個網站主題。今天的屬性是 `data-theme`（HeroUI 慈濟主題用 `tzuchi`、`tzuchi-dark`；`tokens.css` 用 `dark`、`light`）；網站主題要用哪個屬性名稱，待決定。 | 套在內層元素，或同一頁混兩個網站，CSS 的覆寫順序會亂，讀者也分不清是哪個網站。 | 人工檢查，機器檢查尚未實作 |
| R-D-17 | 〔提案，尚未實作〕每個網站的檔案放在 `packages/tokens/src/sites/<id>/`：`theme.light.json`（淺色下和預設不同的值）、`theme.dark.json`（深色下和預設不同的值）、`site.json`（網站名稱和各元件的預設變體）。`<id>` 用小寫英文和連字號（例如 `eco`、`annual-report`），定了就不改。**在實作之前，有人要做某個網站的網站主題時，Claude 先停下來問工程**，不自己建這個資料夾。 | 網站的程式碼會用 `<id>`；建置要怎麼讀這些檔案，還要工程設計。 | 今天沒有這個資料夾 |
| R-D-18 | 〔提案，尚未實作〕網站主題的檔案只寫和預設不同的值，沒寫到的一律退回預設。網站主題只能覆寫**已經存在**的 token 名稱，不能新增名稱。 | 10 到 20 個網站各自新增名稱，kit 就會變成每個網站一套。 | 規劃中：建置時發現不存在的名稱就失敗；今天沒有 |
| R-D-19 | 〔目標：覆寫的順序是專案負責人的決定；檔案的位置是提案，尚未實作〕網站主題先覆寫語意色；只有某個元件仍然需要不同時，才覆寫那個元件的元件 token。網站主題不覆寫基礎 Foundations，值也用參照指向基礎；需要一個基礎裡沒有的值時，先把它加進基礎（R-D-06）。 | 從最上層改，影響最少的檔案；基礎保持所有網站共用。 | 人工檢查，機器檢查尚未實作 |

## 7. 三級判斷：網站之間可以怎麼不同

一個網站想和別的網站不一樣時，依序判斷，**用最低的那一級解決**：

| 級 | 情況 | 怎麼做 |
| --- | --- | --- |
| 第一級 | 只有 CSS 的值不同：顏色、圓角、陰影、邊框、字級、間距 | 這個網站的網站主題：先覆寫語意色；只有某個元件仍然需要不同時，才覆寫它的元件 token |
| 第二級 | 內容一樣，結構或排列不同 | 共用元件的一個變體，並在網站設定檔設這個網站的預設變體 |
| 第三級 | 資料或行為不同，也就是別的網站沒有的東西 | 新元件：通用的直接進 kit；只屬於一個網站業務的，留在那個網站自己的專案，等第二個網站也需要時再移進 kit |

| 編號 | 規則 | 為什麼 | 怎麼檢查 |
| --- | --- | --- | --- |
| R-D-29 | 設計需求依第一級、第二級、第三級的順序判斷，能用低一級解決就不用高一級。 | 越低的級，要維護的東西越少。 | 人工檢查（PR 的「屬於哪一級」那一段） |
| R-D-30 | Claude 必須在動手前問共編者這是第幾級（用下面的問題），並把答案和理由寫進 PR 的「屬於哪一級」：第一級、第二級、第三級，或不適用。共編者不確定時，Claude 說明理由並建議一級，由共編者決定；共編者接受建議就照建議做，仍然不能決定時，照 SOP 第 4 節停下來。 | 級別決定要改哪些檔案；寫進 PR，核可的人才看得出判斷對不對。 | 人工檢查（`.github/pull_request_template.md` 有這一段） |
| R-D-31 | 不可以為某個網站複製一份元件（例如「環保網的按鈕」）。需要不同，就用第一級或第二級；真的是別的網站沒有的東西，才是第三級。 | 複製之後，每次修正都要改好幾份，10 到 20 個網站就改不完。 | 人工檢查，機器檢查尚未實作 |
| R-D-32 | 某個網站不用某個元件時，什麼都不用做：不必為它寫網站主題，也不必設預設變體。 | 只寫需要的東西。 | 人工檢查 |
| R-D-33 | 第三級的新元件，通用的（第二個網站可能也會用）直接進 kit；只屬於一個網站業務的，留在那個網站的專案裡，等第二個網站需要時再移進 kit，移進時照 kit 的規則（變體、token、手冊）整理。網站自己的專案放在哪裡，待決定。 | kit 只放大家共用的東西；只有一個網站用的，放在 kit 裡反而沒人維護。 | 人工檢查 |

### PR 的「屬於哪一級」怎麼寫

| 修改 | PR 寫 |
| --- | --- |
| 改預設網站的 token 值、所有網站一起改 | 不適用 |
| 某個網站只有 CSS 值不同 | 第一級 |
| 為某個網站加變體，或優化元件時加變體 | 第二級 |
| 路線圖上「新增」的元件（通用，進 kit） | 第三級（通用，路線圖 R-xxx） |
| 路線圖上「優化」的元件 | 依補上的東西：只是外觀寫第一級或不適用；加變體或零件寫第二級；加資料或行為寫第三級 |
| 文件、路線圖的狀態、建置與工具 | 不適用 |

### Claude 要問的問題（照字面問）

Claude 依序問，得到答案就停在那一級：

1. 「這是某一個（或某幾個）網站要和其他網站不一樣，還是 kit 本身的修改（所有網站一起改）？」
   - kit 本身的修改 → 不是網站之間的差異，照上表寫（通常是「不適用」；路線圖上的元件照上表），照 token 和變體的規則改預設值。
   - 某些網站要不一樣 → 繼續問。
2. （只有需求和某個元件有關時才問）「這個網站會用到這個元件嗎？」
   - 不會 → 什麼都不用做（R-D-32）。
3. 「畫面上的內容（文字、圖片、資料）和功能都一樣，只是顏色、圓角、陰影、邊框、字的大小或間距不同嗎？」
   - 是 → **第一級**。
4. 「內容一樣，但排列或結構不同嗎？例如圖片在上面還是在左邊、要不要加圖示？」
   - 是 → **第二級**。再問：「這個樣式用在什麼場合、為了什麼目的？我會用這個用途來命名（例如『精選』），不用外觀命名（例如『大紅框』）。」
5. 「這是別的網站沒有的資料或功能嗎？例如要顯示新的資料，或有新的互動方式？」
   - 是 → **第三級**。再問：「以後其他慈濟網站也可能用到它嗎？」會 → 做成 kit 的通用元件；不會 → 留在那個網站自己的專案。

### 例子

| 需求 | 屬於 | 怎麼做 |
| --- | --- | --- |
| 環保網的按鈕顏色和入口網不同 | 第一級 | 環保網的網站主題先覆寫語意色（例如品牌主色）；只有按鈕仍然要不同時，才覆寫按鈕的元件 token。網站主題的檔案還沒有實作，整個需求先停下來問工程（R-D-17）；不先做其中一部分（例如先加基礎色） |
| 文章卡片：入口網圖在上，另一個網站圖在左 | 第二級 | 文章卡片加一個依用途命名的變體（例如用在清單頁的叫「清單」），再在那個網站的設定檔把它設成預設變體 |
| 環保網要一個「減碳計數器」 | 第三級 | 新元件。只有環保網用 → 留在環保網自己的專案；第二個網站也需要時再移進 kit |
| 某個網站沒有文章卡片 | 不必處理 | 什麼都不做：不寫網站主題，也不設預設變體 |
| 「送出」「取消」「更多」三種按鈕 | 不是新元件 | 同一個按鈕的強調程度變體（主要、次要……），文字是內容（R-D-25） |
| 按鈕要「圖示加文字」 | 第二級（同一個按鈕的選項） | 同一個按鈕放不放圖示的選項，不另做元件（R-D-25） |
| 所有網站的次要文字都要調深 | 不適用 | 改預設的語意色 `color.text.muted`，讓它指向較深的基礎灰色（不改基礎值） |
